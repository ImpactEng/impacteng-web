Separating human, agent and CI credentials as a solo operator

How I split one GitHub login into separate credentials for me, my AI coding agents and CI, what the first attempt broke, and where it landed.

Section 01

One login, three actors: separating human, agent and CI credentials when AI agents do the work

I run ImpactEng on my own, and a lot of the hands-on work now goes through AI coding agents. From mid-September I started bringing the pieces together. Most already followed the same conventions. They just didn't share one way in. In October I set out to make that one governed path for deploying infrastructure to every provider I use. One rule sits at the centre: I approve every production deploy.

This post follows an earlier piece, Where AI Agents Break Your CI/CD Pipeline, which looked at the pipeline itself. This one covers the credentials behind it.

Section 02

Where it started

The path covers more ground than a one-person business might suggest. Deploys go to AWS, Cloudflare, GitHub Pages and Google Apps Script. Code lives on GitHub and on a self-hosted Git forge, secrets sit in a password manager, and CI (continuous integration) does the deploying. Several AI coding agents do much of the preparation, Claude Code among them. I wanted one way in, so that at any time I could say what was deployed where, and by whom.

The path as it stands now.

The approval rule matters most to me. An agent can prepare a change; only I let it reach production.

Section 03

Why it changed

Then I looked at what the one GitHub login on my machine could do. Everything: push to any repository and start runs. And every agent session used it, because the agents ran as me.

So in principle an agent could edit the deploy workflow, remove the check that enforced my approval, and start a run. My approval gate meant poop while the agents held the trigger.

Section 04

The first fix: split the login

It looked like an easy fix. Give each actor its own root of trust: me, CI and the agents. My own GitHub login has always lived in my password manager; now the command-line token goes through it too, so using it needs my fingerprint (and a little patience). The agents got a narrow token of their own. CI was planned around short-lived federated credentials through OIDC (OpenID Connect) wherever a provider supports them, so that no long-lived Cloud key has to sit in a repository.

The problem was real, and splitting the login was the right call. The way I did it caused most of what came next. Good intentions, road to hell, you know the rest.

Section 05

What it broke

I removed access without first listing what it was used for. Within days the agents could no longer read CI results or open pull requests. My own login lost access I still need now and then, such as organisation settings. And my tests checked each token's settings. None of them ran a real task, such as an agent opening a pull request.

One gap I knew of and left open. A push over SSH (Secure Shell) doesn't care about token permissions, and I had written that down at the start. It stayed a note until an agent session pushed a branch as me. 🤦

Section 06

Doing it again, from an inventory

Second time round, I started with what we actually used. I went through what the old login had been used for, by me and by the agents, and listed every workflow that touched GitHub: reading CI, opening a pull request, creating a repository, merging, settings. For each one I wrote down how it worked before, after, and how it should work. That table became my test plan.

I also added a guard at the git level so that an agent session doesn't push as me by accident. Its first version rewrote push addresses, and a git setting I hadn't accounted for got round it. The second, which replaced it, refuses the push itself.

GitHub helped with one of the losses. In October it added a narrow Repository creation permission, so I can create repositories again without the wider permission, and the agents still can't. I covered that step in a short LinkedIn post.

One thing I'd recommend: commits made in an agent session are now authored and signed as the agents, under their own name and signing key, but they keep my GitHub noreply email address. The history shows the work as the agents', and by GitHub's rule it should still count on my contribution graph, because GitHub credits a commit by its email address, and the noreply address counts (GitHub Docs).

Section 07

What changed my mind

There was still a gap GitHub couldn't see. The agents' token sat on my own account, so as far as GitHub could tell, everything done with it was done by me. Merging a pull request needed no permission beyond what an agent already held to push a branch. So GitHub couldn't tell an agent's merge from mine. "Agents never merge" only held because the agents behaved.

Turns out this is a known mistake. AWS lists it for IAM (Identity and Access Management) in its guidance for agentic AI: reusing human user credentials or roles for agent authentication, which makes it "impossible to distinguish agent actions from human actions in audit logs" (AWS Well-Architected, Agentic AI Lens).

The pattern I found in vendor docs and in other solo operators' write-ups has three actors and three credentials. The agent works under its own identity and can at most push a branch. The human approves and merges as a different identity. CI holds the deploy credential, through short-lived federation where the provider offers it.

Section 08

Where it landed, for now

By that pattern, the agent needs its own identity. Its commits already carried one, but GitHub's own logs still saw only me. I also started on the shape other solo operators describe: a free machine account as a collaborator with write access, and a main-branch rule requiring a review the agents can't give. Then the merge decision would sit with GitHub.

Setting it up, I had to change the plan twice. The token I meant to give the machine account couldn't be made: a fine-grained token on that account could reach only repositories it owned, and it owns none. And on GitHub's free plans, rulesets are available only on public repositories (GitHub Docs), so on a private repository the review rule isn't enforced. There, any credential that can push a branch can also merge it. Both facts were cheap to check, and I should have checked them before deciding.

So I went with the simplest option, one GitHub doesn't have to enforce: the agents hold no write credential on GitHub, and their old token is revoked. They prepare branches under their own identity, and I push them and merge the pull requests. Read-only access will give them back most of what they lost, since most of what they did on GitHub was reading. If pushing by hand becomes a chore, there is a researched way to split the permissions across two GitHub Apps, so that the one able to open a pull request can't merge it. I haven't tested it yet.

Two things I'm still working out. The first is an operating system boundary for agent sessions, a microVM (a lightweight virtual machine) or a second user account. The second is providers without OIDC. Cloudflare's guide for deploying from CI still asks for an API token stored as a secret (Cloudflare Docs), so for providers like that the plan is to keep the deploy token behind the same approval gate, out of the agents' reach.

Section 09

Over to you

How have you separated human, agent and CI credentials? I'm most interested in solo operators and small teams, and in anyone doing it across several providers at once, where each one has its own idea of identity.

If you've solved this, or you're partway through, I'd like to hear how. Get in touch or book a time to talk.
