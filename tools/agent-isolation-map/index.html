Step 1 of 4

Which risks exist? The triangle

    From Meta's Agents Rule of Two and Simon Willison's lethal trifecta. Meta's guidance is at most two corners in one session without a person checking. All three need a corner removed, or a person at a gate the agent cannot bypass.

    Step 2 of 4

    Where do you cut the chain? The attack path

    Harm usually needs several layers to fail together. Some incidents need no attacker at all: an agent with keys and the ability to delete only needs the right two layers open. In the public incident write-ups reviewed for this map (November 2026), most attacks got in through the left two layers and most damage came out through the right two. The sandbox is one layer of four. The incident names are examples, and some rest on a single source.

    Step 3 of 4

    Sandbox against keys only: which cell are you in?

    Today With the advice applied

    This grid rates only the sandbox against the keys in reach. It leaves out what the agent reads, who shares it and what it can send, so a lower cell is not an all-clear: the six settings above cover the rest. Moving down a column, to a stronger sandbox, never fixes the right-hand column. Moving left, to fewer and weaker keys, helps or holds on every row and never makes things worse. A cell can differ from the verdict above, which counts all your answers. * Agent OS sandboxes usually allow broad reads by default, so deny reads of your secret files explicitly.

    Where your keys live, and how to reduce exposure

    An agent run directly on your machine acts as the account that starts it, so it can use whatever that account can. Denying reads of a folder covers only the first row.

    KindExamplesWhat stops the agent using it
    Files on disk~/.aws/credentials and ~/.aws/config (plain text), the AWS sign-in token cache in ~/.aws/sso/cache, ~/.kube/config when it holds tokens or client keys, gcloud's application_default_credentials.json, the Azure CLI token cache (plain text on Linux and macOS), ~/.npmrc, ~/.pypirc, ~/.git-credentials, ~/.docker/config.json without a credential helper, .env files, the agent's own login file where it keeps one, and MCP configuration files, whose env blocks can hold API keysA sandbox rule that denies reads of these paths. Better still, no long-lived secret in a file at all
    SocketsThe SSH agent socket named in SSH_AUTH_SOCK, including password managers' SSH agents; the Docker socketKeep the socket out of the agent's box. Denying ~/.ssh does nothing here: a process that can reach the socket can sign as you without reading any key file
    EnvironmentCloud keys and API tokens in variables the agent inherits, including secrets injected by tools such as op run or doppler runInject a secret into the one command that needs it, not into the agent's own process, and make sure the agent cannot run the same tool in an already-authorised session
    SessionsA signed-in browser profile; a password manager's or secrets tool's command-line session already unlocked in that terminal (some stay unlocked for minutes or hours: check your tool's timeout)Start agents in a fresh terminal and a separate browser profile

    Tools that reduce key exposure

    Most of these shorten how long a key works or keep it off disk. Only a separate identity for the agent keeps your own keys out of its reach, and none of them protects a secret handed to the agent's own process.

    PatternExamplesWatch for
    An SSH agent that asks before each use of a keyA password manager's SSH agent (1Password and Bitwarden both offer one), keys added with ssh-add -c, which asks for confirmation, or a FIDO security key (ed25519-sk) that needs a touch for each signatureSome approve an app and everything it starts until the vault locks. Choose approval per terminal session or per request where offered, keep the touch requirement on hardware keys, and don't start an agent in a terminal that is already approved
    Short-lived cloud credentialsYour cloud's own short-lived sign-in: on AWS, IAM Identity Center (sessions of 1 to 12 hours); on Google Cloud, service account impersonation, whose credentials last a few hours or less; on Azure, Microsoft Entra Privileged Identity Management, which activates a role for a set time. Also aws-vault and HashiCorp Vault leasesShort-lived still means usable for the whole session
    A separate identity for the agent1Password service accounts limited to chosen vaults, HashiCorp Vault, Bitwarden Secrets Manager machine accountsGive the agent its own identity rather than a person's login
    Secrets fetched at run timeop run, doppler runThe secret lands in that process's environment, so run it for the one command, not for the agent, and not where the agent can run it too

    Sandboxes you can put an agent in

    A microVM gives each sandbox its own kernel, but outbound access and where the keys sit are separate choices, and the defaults differ.

    SandboxDefault, as of 2026-11Source
    Docker SandboxesEach sandbox is its own microVM with a separate kernel. Outbound TCP is blocked unless a rule allows it, UDP is off, ICMP is blocked and DNS goes through an internal resolver. A host proxy injects credentials so the values never enter the VM. The default allowlist includes broad wildcards such as *.googleapis.com, and sbx run mounts the current directory read-write. Before v0.51.0, a malicious sandbox could use a symlink to make a later sbx cp read or write host files outside the workspace (CVE-2026-103916).defaults; security; NVD
    Vercel SandboxEach sandbox is its own Firecracker microVM with a dedicated kernel. Outbound HTTP is allowed by default; a network policy is optional. Firewall rules that terminate TLS on the way out can inject credentials. A Trail of Bits review judged the virtualisation boundary sound. The bounty's worst finding, a Linux kernel networking zero-day, gave host command execution on the researcher's replica machines and leaked host memory from Vercel's production sandboxes. Vercel published both, so it is not a neutral audit.security; challenge findings

    Terms used on this page
    Prompt injection
    Instructions hidden in content the agent reads, such as a web page or an issue, that steer it.
    OS sandbox
    Operating system limits on a process, such as Seatbelt on macOS, bubblewrap on Linux or Microsoft Execution Containers (MXC) on Windows. Usually wraps the agent's shell commands, not the agent itself.
    Container or VM
    A separate environment for the whole agent. A container shares the host's kernel; a virtual machine (VM) has its own. The UK's NCSC ranks a VM above a container (2026-08-20); this map keeps them at one level because its main point is that keys and outbound access matter more than the box.
    microVM, gVisor
    Lightweight isolation built for running untrusted code from many users: microVMs (such as Firecracker) give each session its own small VM, and gVisor puts a user-space kernel in front of the host's. NVIDIA's AI Red Team rates gVisor's guarantees as "potentially weaker" than full virtualisation (2026-01-30); this map groups the two for simplicity.
    Brokered keys
    The real secret stays outside the sandbox. A proxy attaches it to approved requests, or the agent gets a short-lived token scoped to one job.
    Permission ceiling
    A limit set above an account or project that caps what any identity in it can do, whatever its own permissions say. On AWS, a service control policy (SCP) caps IAM users and roles in a member account, including the account's root user; service-linked roles and the organisation's management account are not bound by it. On Google Cloud, an IAM deny policy attached to a project, folder or organisation does a similar job.
    Shared account
    When an assistant serves many people through one account, anyone who can talk to it can reach whatever that account can. Acting with each user's own access avoids this.
    Outbound allowlist
    A list of the only hosts the agent may connect to. It still leaks through allowed hosts that accept user content.
    Rule of Two
    Meta's guidance: within one session an agent should have at most two of untrusted input, sensitive data, and the ability to act or communicate.

    About these rules

    What the map is, and is not

    Rules version 2026-11, revision 6 (2026-11-21). The map draws together public sources read in November 2026. No authority publishes rules like these as a whole; the nearest is the NCSC's pair of four-level scales, one for the sandbox and one for network access (see the terms under Reference). The rules are kept simple on purpose. Treat each answer as the start of a conversation, not the final word.

    It covers isolation: what an agent can reach and do. It does not cover what a chatbot says, such as a wrong promise to a customer, which is a content and liability question.

    If you use a model built or tuned for security work, use the strongest sandbox, keep nothing worth stealing inside it, and block outbound traffic by default, allowing only the model's own endpoints and what the job needs. In one published lab test (Trail of Bits, 2026-08-26), a cyber-capable model escaped QEMU virtual machines, including one rebuilt from current source. It did not escape a Firecracker microVM in that run, though it hard-locked the host through Linux kernel flaws. One author, one model, lab conditions.

    Your answers stay in this page: nothing you choose is sent or stored, and the address does not carry them. Site analytics counts that the map was used and the risk level it gave, in one word.

    Changes

    How the rules have moved

    • Revision 6, 2026-11-21. An agent that runs code now always counts as able to act, including one that many people share. Before, sharing such an agent could lower its settings while its risk rose. Some settings rise and no risk level changes. A new check confirms that no change the map suggests ever raises the risk level. On the attack path, Reaches is open whenever the agent can read private data, and Gets out is closed once the gate and outbound control in place meet the settings.
    • Revision 5, 2026-11-20. An unattended agent that runs code on input a stranger can aim at needs at least an outbound allowlist, even with nothing private to leak.
    • Revision 4, 2026-11-12. Two questions record the human gate and outbound control already in place, and the risk that remains is shown with those counted.
    • Earlier. Three levels of untrusted input; keys judged by the worst thing they allow, whatever their lifetime; a sixth setting, recover and notice; an OS sandbox as the floor for any agent that runs code; a browser agent type.
